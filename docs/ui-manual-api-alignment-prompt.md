```markdown
# 任务：UI ↔ 手册 / API / 前端 对齐审计（只读）

## 目标

对照本仓 **已实现的 UI 功能**，同时产出三张表（**都必须有**）：

1. **表 A**：手册 / API **未提供**或 **提供错误**（含手册↔API 打架、同文档自相矛盾）
2. **表 B**：前端可独立修复（接错、语义错、缺接线）——**且不必改用户可见文案**
3. **表 C 📝**：纯文案问题；须 **链上 + Figma + API** 联合确认 **无法对接**（本仓**不改文案**）

保存到 `docs/`（kebab-case，可覆盖或日期版）。**禁止改业务代码、禁止改手册正文、禁止改 OpenAPI、禁止改 i18n/Figma 文案。**

## 需求基线

1. **以 UI 已实现功能为准**（设计稿已定）。只审 UI 里已有的动态数据展示与读写能力。
2. 手册/API 是对照源，不是需求源：稿有控件 → UI MUST；数跟手册/API/链。
3. **故意对无数据源显示 `0`** → 设计取舍，**各表都不报**。
4. 「大体对齐」**不算过关**；只有确认完全正确才不进表。有疑点就进表并标明。
5. **不能改文案**：单位标签 / FAQ / 断言句若与链冲突，且改接线无法让现有措辞变真 → **C 📝**，禁止塞进 B「如何对齐：改 i18n」。

## 对照优先级（判断对错）

1. **BSC 链上 view / ABI**（最高；手册/API 与链冲突时 **FE 跟链**，文档问题进表 A）
2. `docs/onchain-manual/`（入仓只读，**禁止改写**）→ legacy 仅补缺口
3. `docs/backend-api/`（以 `openapi.json` 为准）
4. **Figma / i18n**：稿有控件 → UI 保留；措辞与链冲突 → **冲突表（可列不修）**，不进需修复 B

## 三表分工

| 表           | 进表                                   | 硬门槛                        |
| ------------ | -------------------------------------- | ----------------------------- |
| **A**        | 手册/API 缺口或相对链错误              | 不写「请改手册」              |
| **B 需修复** | 跟链改取数/门闸/缓存，不改布局文案     | 「只改 FE 跟链能合 PR？」→ 能 |
| **冲突表**   | 设计如此；或稿文案与链冲突（不改文案） | **可列、不进需修复**          |

### 表 A 分类

| Emoji | 含义                                                                           |
| ----- | ------------------------------------------------------------------------------ |
| 📭    | UI 已有该能力，手册与 API 皆无可用定义/字段；或链/API **尚未提供**修好所需能力 |
| ❌    | 手册或 API 有定义，但与链上不符                                                |
| ⚔️    | 手册与 API 都写了但互相矛盾                                                    |
| 🌀    | 同一侧文档内部冲突                                                             |

### 表 B 分类

| Emoji | 含义                                                |
| ----- | --------------------------------------------------- |
| 🐛    | 实现错误（本仓可改，**如何对齐禁止写改文案**）      |
| 🔌    | 缺接线 / 入口误导（接通**已有**能力，或先下架入口） |

### 表 C 分类

| Emoji | 含义                                                        |
| ----- | ----------------------------------------------------------- |
| 📝    | 纯文案/单位标签/FAQ；三方确认无法对接；等产品改稿后方可关闭 |

**禁止**把「等新 API / 新交易路径」写进 B。可拆行：能力 → A；接线 → B；文案无法对接 → C。

### 同题多行（允许且推荐）

例：释放池 API 标 gAGX（**A-12** ❌），Figma/i18n 也写 gAGX 且不能改文案（**C-07** 📝）。  
例：卖 X 路径不存在（**A-02** 📭），卡片误导已下架（**B-03** 🔌）。  
例：溢价率标签可保留、只改计算公式 → **B**（不是 C）。

### 编号

每行 `A-01`… / `B-01`… / `C-01`…；新增接续；关闭/迁出不复用；交叉写「见 A-xx / B-xx / C-xx」。

## 审查范围

`src/views/dapp/`：exchange / staking / assets / rewards / release / community / genesis  
（host 全局态若影响页内数据一并审。）

每页：动态字段含义、读源（链/API）、写路径；文档是否有定义、是否与链一致；FE 是否跟对；文案是否与链冲突。

## 方法

1. codegraph 定位页内数据与写路径；读手册章节 + `docs/backend-api/api.md`。
2. 争议项 **链上核实**（地址 `VITE_BSC_*` / `contracts.ts`；`getConfig` 类勿写死 env 代币）。
3. 疑似文案项：打开对应 **Figma 节点** + `zh.ts` 关键词，再对 API 字段说明。
4. 先填表 A，再填表 B，最后填表 C；FE 跟错错误文档时 A+B 或 A+C。
5. 落盘审计 md；提示词有更新则同步本文件；`docs/README.md` 可补索引一行。

## 产出格式（必须三表齐全）

### 1. 链上核实锚点（抽样）

| 项  | 链上结果 |
| --- | -------- |

### 2. 表 A — 手册 / API / 链缺口

每行 `A-01`…。必须含普通人能懂的 **问题描述** 与 **造成的结果**。

| ID  | 分类 | 页面 | 问题描述 | 造成的结果 | 备注 |
| --- | ---- | ---- | -------- | ---------- | ---- |

### 3. 表 B — 前端可独立修复（必出）

每行 `B-01`…。必须含 **问题描述**、**造成的结果**、**如何对齐（仅前端·不改文案）**。关联缺口写 A-xx。

| ID  | 分类 | 页面 | 问题描述 | 造成的结果 | 如何对齐（仅前端·不改文案） | 关联 |
| --- | ---- | ---- | -------- | ---------- | --------------------------- | ---- |

### 4. 表 C — 📝 纯文案无法对接（必出；可为空表但须声明已筛）

每行 `C-01`…。必须含 **三方确认** 与 **为何无法对接**。

| ID  | 页面 | 问题描述 | 造成的结果 | 三方确认（链上 · Figma · API） | 为何无法对接（不改文案） | 关联 |
| --- | ---- | -------- | ---------- | ------------------------------ | ------------------------ | ---- |

### 5. 阻塞·待产品（可选短表）

须产品定 SSOT、且无安全 FE 临时修法时才列；**不要**塞进表 B。表 C 文案纠偏属产品改稿。

### 6. 不在表内（短声明）

故意 `0`/`—`、已确认正确主路径、非本仓改手册/API/文案职责。

## 禁止

- 改 `docs/onchain-manual/**`、改 `openapi.json` 正文、改 i18n/Figma 文案。
- 未核实链上就断言文档错或实现错。
- 未核实 Figma+API 就把文案项塞进 C。
- 只出表 A 不出表 B/C（或把 FE bug 塞进表 A；或把改文案写进 B）。
- 表 B「如何对齐」里写改手册/改 API/改文案。
- 无用户明示不 commit / push。

## 收工

① 写了哪份 docs ② 表 A 条数（按 emoji）③ 表 B 条数（按 emoji）④ 表 C 条数 ⑤ 一句「未改代码/手册/API/文案」。
```
