```markdown
# 任务：UI ↔ 手册 / API / 前端 对齐审计（只读）

## 目标

对照本仓 **已实现的 UI 功能**，同时产出两张表（**都必须有**）：

1. **表 A**：手册 / API **未提供**或 **提供错误**（含手册↔API 打架、同文档自相矛盾）
2. **表 B**：前端实现错误（接错、语义错、缺接线）

保存到 `docs/`（kebab-case，可覆盖或日期版）。**禁止改业务代码、禁止改手册正文、禁止改 OpenAPI。**

## 需求基线

1. **以 UI 已实现功能为准**（设计稿已定）。只审 UI 里已有的动态数据展示与读写能力。
2. 手册/API 是对照源，不是需求源：稿有控件 → UI MUST；数跟手册/API/链。
3. **故意对无数据源显示 `0`** → 设计取舍，**两表都不报**。
4. 「大体对齐」**不算过关**；只有确认完全正确才不进表。有疑点就进表并标明。

## 对照优先级（判断对错）

1. **BSC 链上 view / ABI**（`cast call` 等核实）
2. `docs/onchain-manual/`（入仓只读，**禁止改写**）→ legacy 仅补缺口
3. `docs/backend-api/`（以 `openapi.json` 为准）

钱路：手册有 → 按手册语义；手册沉默且 API 有 → 按 API 是否自洽；皆无 → 表 A 记 📭；与链冲突 → 表 A 记 ❌，若 FE 还跟错了文档 → 表 B 另记一行。

## 两表分工（禁止混表）

| 表                    | 进表                                                                                      | 硬门槛                                                                  | Emoji       |
| --------------------- | ----------------------------------------------------------------------------------------- | ----------------------------------------------------------------------- | ----------- |
| **A 手册/API/链缺口** | 未提供 / 提供错误 / 两边打架 / 同文档自相矛盾；**以及修好必须链上或 API 先给能力/改字段** | 只描述问题，**不写**「请改手册第×节」                                   | 📭 ❌ ⚔️ 🌀 |
| **B 前端可独立修复**  | 本仓前端现在就能合入的修复                                                                | 问「只改 FE 能合 PR 吗？」→ **能**才进 B；不能 → 进 A 或「阻塞·待产品」 | 🐛 🔌       |

### 表 A 分类

| Emoji | 含义                                                                           |
| ----- | ------------------------------------------------------------------------------ |
| 📭    | UI 已有该能力，手册与 API 皆无可用定义/字段；或链/API **尚未提供**修好所需能力 |
| ❌    | 手册或 API 有定义，但与链上不符                                                |
| ⚔️    | 手册与 API 都写了但互相矛盾                                                    |
| 🌀    | 同一侧文档内部冲突                                                             |

### 表 B 分类

| Emoji | 含义                                                   |
| ----- | ------------------------------------------------------ |
| 🐛    | 实现错误（本仓可改）                                   |
| 🔌    | 缺接线 / 入口误导（接通**已有**能力，或先下架/改文案） |

**禁止**把「等新 API / 新交易路径」写进 B 的「如何对齐」。可拆行：能力 → A；入口诚实/跟错展示 → B。

### 同题两行（允许且推荐）

例：释放池 API 标 gAGX（**A-12** ❌），FE i18n 也写 gAGX（**B-28** 🐛，FE 先跟链改 AGX）。  
例：卖 X 路径不存在（**A-02** 📭），卡片误导（**B-03** 🔌 只下架/改文案）。

### 编号

每行 `A-01`… / `B-01`…；新增接续；关闭不复用；交叉写「见 A-xx / B-xx」。

## 审查范围

`src/views/dapp/`：exchange / staking / assets / rewards / release / community / genesis  
（host 全局态若影响页内数据一并审。）

每页：动态字段含义、读源（链/API）、写路径；文档是否有定义、是否与链一致；FE 是否跟对。

## 方法

1. codegraph 定位页内数据与写路径；读手册章节 + `docs/backend-api/api.md`。
2. 争议项 **链上核实**（地址 `VITE_BSC_*` / `contracts.ts`；`getConfig` 类勿写死 env 代币）。
3. 先填表 A，再填表 B；FE 跟错错误文档时两表都记。
4. 落盘审计 md；提示词有更新则同步本文件；`docs/README.md` 可补索引一行。

## 产出格式（必须两表齐全）

### 1. 链上核实锚点（抽样）

| 项  | 链上结果 |
| --- | -------- |

### 2. 表 A — 手册 / API / 链缺口

每行 `A-01`…。必须含普通人能懂的 **问题描述** 与 **造成的结果**。

| ID  | 分类 | 页面 | 问题描述 | 造成的结果 | 备注 |
| --- | ---- | ---- | -------- | ---------- | ---- |

### 3. 表 B — 前端可独立修复（必出）

每行 `B-01`…。必须含 **问题描述**、**造成的结果**、**如何对齐（仅前端）**。关联缺口写 A-xx。

| ID  | 分类 | 页面 | 问题描述 | 造成的结果 | 如何对齐（仅前端） | 关联 |
| --- | ---- | ---- | -------- | ---------- | ------------------ | ---- |

### 4. 阻塞·待产品（可选短表）

须产品定 SSOT、且无安全 FE 临时修法时才列；**不要**塞进表 B。

### 5. 不在表内（短声明）

故意 `0`/`—`、已确认正确主路径、非本仓改手册/API 职责。

## 禁止

- 改 `docs/onchain-manual/**`、改 `openapi.json` 正文。
- 未核实链上就断言文档错或实现错。
- 只出表 A 不出表 B（或把 FE bug 塞进表 A）。
- 表 B「如何对齐」里写改手册/改 API。
- 无用户明示不 commit / push。

## 收工

① 写了哪份 docs ② 表 A 条数（按 emoji）③ 表 B 条数（按 emoji）④ 一句「未改代码/手册/API」。
```
